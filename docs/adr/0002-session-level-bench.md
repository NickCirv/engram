# ADR-0002: Session-level token bench (deterministic trace replay)

**Status:** Accepted · **Date:** 2026-06-03 · **Author:** Nicholas

## Context

`bench/real-world.ts` measures *per-file* structural reduction (packet vs raw file). It cannot answer
the question engram's whole thesis rests on: does intercepting the agent's investigation *loop*
(`grep → read → read`) reduce the **total tokens of a session**? The live LLM benchmark suite
(`engram-benchmarks`, W1.x) tried to answer the cost version and got a muddy result — engram's net over
Anthropic prompt caching was +6.49%, CI [−5.35, +18.33], indistinguishable from zero — because it
conflated three things at once (caching, per-file reduction, and the agent's behavioural trajectory)
and was N=1–3 noisy. We need a *deterministic, reproducible, free* instrument that isolates the
mechanical session-level reduction without the LLM noise.

## Decision

Build `bench/session-level.ts`: replay **machine-generated investigation traces** through engram's
**real shipped handlers** (`handleRead`, `handleGrep`), counting total tool-call tokens in two arms —
baseline (no engram) vs engram — over the **same fixed tool sequence**.

- **Traces are generated by a rule, never hand-picked:** rank symbols by how many files reference them
  (incoming `calls` edges), take the top K, and for each emit the trace `Grep(symbol) → Read(top-3
  caller files)` — "investigate how this important symbol is used." A control set of text-search traces
  (a common word + a small file) is included so the report shows the full honest range, not just wins.
- **Baseline arm:** `Grep` = real `ripgrep` output tokens; `Read` = full file tokens.
- **Engram arm:** each call goes through the real handler — `deny` → packet tokens, `passthrough` →
  same as baseline.
- **Token heuristic:** `ceil(text.length / 4)`, identical to `real-world.ts`.

## The trade-off (what this bench is and is NOT)

**Correction (2026-06-03, after adversarial audit):** an earlier draft of this ADR called the
fixed-sequence bench a "conservative lower bound." That was **wrong, and backwards.** engram's packet is
a *subset* of the raw tool output — the grep packet is a ranked file list (not the match lines), the
read packet is a structural summary (not the file's literal text, and provably does not contain the
investigated symbol's call site). So when the agent's real information need is not in the packet, it
re-runs the raw call **on top** of the packet. A bench that assumes the packet always substitutes is an
**OPTIMISTIC UPPER BOUND**, not a lower bound.

So the bench does not report a single number. It reports the session reduction as a function of
**P = the fraction of intercepted calls where the agent still needs the raw content**:

```
engram_cost(step, P) = intercepted ? packet + P*baseline : baseline
```

- `P = 0` — packet always suffices (optimistic ceiling).
- `P = 1` — agent always needs raw too → engram is pure overhead (negative reduction).
- **break-even P** = `(interceptedBaseline − interceptedPacket) / interceptedBaseline` — the fallback
  rate below which engram still nets positive. This is the honest headline.

The break-even P being high (e.g. ~0.89 on engram's own repo) is the defensible claim: the packet is so
much smaller than the raw output that engram nets positive unless the agent re-fetches raw content on
most intercepted calls. The recall-sufficiency is workload-dependent — high on structural/discovery
investigation, low when exact call sites are needed — which is the same bimodal split the live
bench found (+24% troubleshooting / −9% refactor). The symbol-grep baseline uses word-boundary `rg -w`
(apples-to-apples with engram's symbol answer). This is a *structural* context-token reduction, not a
bill saving (caching owns cost; net ≈ 0). The live LLM-in-the-loop bench (`engram-benchmarks`)
remains the gold standard for behavioural reality; this deterministic bench complements it by isolating
the mechanical reduction and its sensitivity to recall-recovery.
